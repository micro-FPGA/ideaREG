## Idea

### Title

**MicroFPGA** — making FPGAs programmable in C without HDL, by using ASIO as the universal hardware interface and pre-built bitstreams as the deployment model.

### Description

MicroFPGA is a concept for an FPGA development model that allows engineers to use FPGAs without writing any hardware description language (HDL) code. The model uses three components together:

**1. Pre-built bitstreams.** For each supported FPGA device or development board, a bitstream is pre-generated containing:
- A processor (hard processor like Zynq's ARM core, or a soft processor like MicroBlaze or RISC-V)
- An ASIO instance (or multiple instances) connected via AXI-Lite to the processor
- All available FPGA package pins routed to ASIO's GPIO ports
- Required clock infrastructure and reset logic

Users do not generate this bitstream themselves. They download the appropriate bitstream for their board and program it once.

**2. C library for ASIO access.** A library that exposes ASIO's pin-level control through familiar C functions:
- Low-level: `asio_write(pin, value)`, `asio_read(pin)`
- Higher-level protocol implementations: `uart_init()`, `uart_tx_byte()`, `i2c_init()`, `i2c_write()`, `spi_transfer()`, and so on
- Bit-banging timing routines that achieve the maximum reliable rates for common protocols on the target processor

**3. Simplified toolchain.** A development workflow that hides the FPGA complexity:
- Download the bitstream for the target board (one-time setup)
- Write C code using the MicroFPGA library
- Compile with standard C tools (GCC or vendor-provided cross-compiler)
- Load the C binary onto the processor (typically through JTAG or USB)
- Run

The user's experience is similar to programming a microcontroller. They never see HDL, never run synthesis or place-and-route, never deal with timing constraints or pin assignment files. The FPGA appears as a microcontroller with hundreds of GPIO pins instead of dozens.

### Why this idea matters

**The HDL barrier excludes many developers from FPGA use.** Embedded developers, software developers, hobbyists, students, and engineers from adjacent fields often need many GPIO pins for their projects. FPGAs can provide hundreds of pins at low cost, but the HDL learning curve and the synthesis toolchain complexity are substantial barriers. Many developers who would benefit from FPGA pin counts default to multiple microcontrollers or to GPIO expander chips instead.

**The bit-banging model works for many practical use cases.** Common protocols like UART (up to a few Mbit/s), I2C (standard and fast modes), SPI (at moderate rates), 1-Wire, and basic GPIO control of LEDs, switches, motors, and sensors can all be implemented through bit-banging from a processor with sufficient performance. The Arduino and Raspberry Pi ecosystems have demonstrated this across thousands of projects.

**ASIO is the natural foundation.** ASIO's design — one address per pin, write to make output, read to make input — produces software that is straightforward to write and to read. Bit-banging libraries built on ASIO are simpler than the same libraries built on conventional GPIO peripherals with their multi-bit registers and read-modify-write requirements.

**The technical pieces all exist.** Soft processors, AXI-Lite GPIO, C cross-compilers, FPGA programming tools — all of these are mature components. What does not exist is a turnkey product that combines them into the *FPGA-as-microcontroller* experience that MicroFPGA describes.

### Application domains

MicroFPGA is appropriate for use cases that need:
- Many GPIO pins (more than typical microcontrollers offer)
- Software simplicity (developers comfortable with C but not with HDL)
- Modest protocol speeds (bit-banging works for protocols up to a few Mbit/s)
- Tolerance for software-based timing (asynchronous protocols, slow-changing signals, periodic polling)

Specific application categories:
- Hobbyist and educational projects requiring many pins
- Industrial automation with many slow sensors and actuators
- Test and measurement equipment with many independent channels
- Prototyping and exploration before committing to full HDL design
- System integration testing with many monitored or stimulated signals
- Multi-channel displays, indicator arrays, and similar I/O-heavy applications

### Limitations and where MicroFPGA does not apply

MicroFPGA is not suitable for:
- **High-speed protocols.** Bit-banging cannot match dedicated hardware speeds. Use traditional HDL design for PCIe, USB 3.x, Ethernet, high-speed serial, DDR memory, etc.
- **Hard real-time systems.** Software-based timing has variability that hardware does not.
- **Power-constrained applications.** The continuously running processor consumes more power than dedicated hardware would.
- **DSP-heavy applications.** The FPGA's parallel processing capability is not used in the MicroFPGA model.
- **Applications needing FPGA-specific hardware features.** Transceivers, DSP blocks, hard PCIe controllers, and similar specialized resources are not accessed through ASIO.

For these applications, traditional HDL-based FPGA development remains the right approach. MicroFPGA addresses a specific gap, not the entire FPGA development landscape.

### Reference to related ideas and prior art

- **Arduino.** The closest conceptual analogue. Arduino's value proposition is *programming pin-controlled hardware with simple software*. MicroFPGA extends this concept to FPGA-scale pin counts.
- **Raspberry Pi GPIO.** Memory-mapped per-pin access from a Linux process, with substantial community-developed bit-banging libraries. MicroFPGA brings the same model to FPGAs with much higher pin counts.
- **MicroBlaze + AXI GPIO.** The basic pattern (soft processor plus memory-mapped GPIO) already exists in the AMD/Xilinx ecosystem. MicroFPGA's contribution is the productisation — turnkey bitstreams, simplified toolchain, accessible documentation — that does not currently exist as a unified product.
- **Various FPGA development frameworks** (LiteX, Litex/Migen, Chisel, SpinalHDL, Amaranth/nMigen, BlueSpec). These provide alternatives to traditional Verilog/VHDL but still require some HDL-like thinking. MicroFPGA goes further by eliminating HDL entirely from the user's experience.
- **ASIO (A Simple I/O).** The IP core that MicroFPGA depends on, registered in this same ideaREG repository on 2026-05-08. ASIO's design choices specifically enable the MicroFPGA model — one address per pin, simple software access, scalability to hundreds of pins.

The specific contribution of MicroFPGA is the combination: pre-built bitstreams + ASIO + C library + simplified toolchain, presented as a unified product that turns FPGAs into microcontrollers-with-many-pins for the developer's experience.

### What would be needed to develop this into a product

The technical components all exist. The work to turn the concept into a usable product is in productisation:

- Pre-built bitstreams for specific FPGA boards (starting with a few popular development boards and expanding from there)
- A C library implementing the ASIO interface and common bit-banged protocols
- Toolchain integration that makes the workflow as simple as Arduino IDE or PlatformIO
- Documentation aimed at the target audience (engineers comfortable with C but not with HDL)
- Example projects covering common use cases
- Optional: visual programming environment for users who prefer block-based programming over C

The work is moderate but not trivial — probably several months of focused engineering effort to reach a first usable release.

## Remarks

This registration captures the MicroFPGA concept as it stood on 2026-05-08, the day the ASIO IP core was completed and verified in simulation. The concept emerged naturally from thinking about what ASIO could enable beyond its original use cases.

The author is registering the concept publicly without committing to develop it personally. Whether MicroFPGA becomes a real product depends on whether someone — possibly the author, possibly someone else — invests the time required to build the productisation around the technical components. The registration ensures that the concept remains in the public commons regardless of who eventually pursues it.

The name *MicroFPGA* resonates with the existing *micro-FPGA* GitHub organisation that hosts ASIO, ULi, ideaREG, and other related projects. If MicroFPGA is developed further, the natural home for the project would be within that organisation, alongside the technical components it depends on.

The MIT license under which this registration is made allows free use, modification, and commercial development by any party. Any developer or company that wants to build the MicroFPGA product can do so without licensing concerns related to this registration.
