## Idea

### Title

**meM (micro embedded Matrix)** — FPGA emulation of Renesas GreenPAK programmable mixed-signal devices, with bitstream compatibility allowing GreenPAK Designer to be used as the design tool.

### Description

meM is an FPGA-based emulation of Renesas GreenPAK programmable mixed-signal devices. The implementation accepts the configuration bitstream produced by GreenPAK Designer (the standard design tool for Renesas GreenPAK chips) and executes the design on FPGA hardware as if it were running on real GreenPAK silicon.

The project exists as an open-source repository at **github.com/micro-FPGA/meM**, with initial development in 2018. A proof-of-concept design exists and demonstrates the bitstream-compatible emulation working for the supported subset of GreenPAK features. The implementation is not fully completed — not all GreenPAK variants and not all features within supported variants are implemented to production quality.

**The GreenPAK context:**

Renesas GreenPAK (originally Silego, before Renesas acquired the company) is a family of small programmable mixed-signal devices that combine digital logic blocks, analog blocks (comparators, ADCs, DACs, references), and configurable routing. The devices are typically one-time-programmable in production volumes, with reprogrammable variants available for development. GreenPAK fills a specific niche in the embedded systems market — too small and too cost-sensitive for FPGAs, too configurable for fixed-function ICs, often replacing multiple discrete components in a single package.

The GreenPAK Designer software is the standard tool for creating GreenPAK designs. It provides a schematic-style entry environment where engineers connect logic and analog blocks, configure their parameters, and generate the bitstream that programs the device. The bitstream is a binary representation of the configuration that the GreenPAK silicon reads to set up its internal connections and block behaviours.

**The bitstream compatibility claim:**

meM's distinctive feature is bitstream compatibility with GreenPAK Designer. Engineers create their design in GreenPAK Designer using the familiar tool. They generate the bitstream as they would for a real GreenPAK chip. They load that same bitstream into the meM FPGA emulation. The FPGA executes the design as the GreenPAK would have executed it.

This is a substantive technical claim. Bitstream compatibility requires meM to faithfully implement the GreenPAK architecture — the specific macro cells, the routing fabric, the configuration interface, the timing characteristics. The implementation must understand the bitstream format as GreenPAK Designer produces it and must produce GreenPAK-equivalent behaviour for each configuration the bitstream encodes.

**Why FPGA emulation of GreenPAK matters:**

Several specific use cases benefit from FPGA emulation of GreenPAK:

**Development without GreenPAK hardware.** Engineers prototyping GreenPAK designs can use FPGA development boards they already have, without purchasing GreenPAK programmer hardware or sample chips. This accelerates the early development phase.

**Production deployment on FPGA.** Applications that need GreenPAK functionality but want the reprogrammability of an FPGA can deploy the design on meM-equipped FPGA hardware. The design remains modifiable through GreenPAK Designer while running on FPGA silicon.

**Integration with larger FPGA designs.** Engineers building FPGA-based systems can include GreenPAK-style functionality as one component of a larger design. The meM emulation becomes a module within the overall FPGA project, with the GreenPAK part of the design developed in GreenPAK Designer and the larger system developed in conventional FPGA tools.

**Educational visibility.** The meM implementation makes GreenPAK's internal structure visible in a way that proprietary silicon does not. Students and engineers studying programmable mixed-signal devices can examine the meM source to understand how the architecture works.

**Migration paths.** Designs that outgrow GreenPAK's capabilities can transition to meM-on-FPGA as an intermediate step, gaining the FPGA's flexibility while preserving the existing GreenPAK design investment.

### Implementation status

The meM repository at github.com/micro-FPGA/meM contains the proof-of-concept implementation as it stood in 2018. The work demonstrates the core concept — bitstream-compatible emulation of GreenPAK on FPGA — but is not a fully completed product.

Specific limitations of the current proof-of-concept:

- Not all GreenPAK variants are supported. The GreenPAK family includes many specific part numbers with different combinations of resources. The proof of concept addresses a subset of the family.
- Not all features within supported variants are fully implemented. Some specific macro cells, configuration options, or timing modes may not be emulated to full GreenPAK fidelity.
- The implementation has not been tested against the full GreenPAK regression suite. Some edge cases in GreenPAK behaviour may not be replicated correctly.
- Production deployment has not been validated. The proof of concept demonstrates that the approach works; commercial deployment would require additional engineering to verify behaviour across the full range of GreenPAK designs.

The 2018 development phase produced the working core. The work has not been actively developed since then. Whether meM gets further developed depends on whether the registrant or another contributor takes up the project.

### Domain or field

FPGA emulation of proprietary programmable devices, Renesas GreenPAK ecosystem, programmable mixed-signal devices, bitstream-compatible reimplementation, open-source hardware development.

Project Trellis for Lattice ECP5, IceStorm for Lattice iCE40, and similar projects have demonstrated that bitstream-level compatibility is achievable for FPGA architectures. meM extends this practice to the GreenPAK case.

The 2018 work represents an earlier moment in the registrant's engineering practice when projects like meM were being developed but not yet documented through the kind of careful public registration that ideaREG now enables.

## Remarks

This registration documents meM as it currently exists — an open-source proof-of-concept implementation on GitHub with bitstream-compatible GreenPAK emulation, developed in 2018 and not completed to full production quality. The registration is partly retrospective documentation of work that was done years ago without public registration at the time, and partly forward-looking — making the work visible in ideaREG so that future engagement with the project has a clear public reference point.

**On the registration's retrospective character.** Many of the registrations made in this session capture ideas at the moment of articulation, with the registration being part of the idea's emergence into public form. meM is different. The work has existed publicly since 2018 on GitHub. The registration here is documentation of work that already exists rather than introduction of a new idea. This is more like the PINAPI registration (which captured a 1990 engineering practice into the registry retrospectively) than like the MOTUPER registration (which reserved a name for a future concept). The registry can accommodate both kinds of registration.

**On the incomplete proof-of-concept status.** The honest framing — that meM exists, works for the supported subset of GreenPAK features, but is not a fully completed product — is preserved in the registration. The registry's value comes partly from honest framing of the actual status of registered ideas. Pretending meM is more complete than it is would not serve readers who arrive at the registration expecting to find production-ready code. The honest status lets readers know what to expect when they visit the GitHub repository.

**On the relationship to Renesas.** meM emulates a Renesas product without Renesas's involvement. The implementation is the registrant's own engineering work, distributed under open-source terms, available to anyone who wants to use it. Renesas's GreenPAK product line is unaffected by meM's existence — engineers can still use real GreenPAK chips, the GreenPAK Designer software remains the standard tool, the GreenPAK business operates as it always has. meM provides an alternative deployment target for designs created with Renesas's tool, without claiming any official relationship with Renesas.

**On potential future development.** meM has been dormant since the 2018 proof-of-concept work. Whether it gets further developed depends on whether the registrant returns to it or whether another contributor picks it up. The MIT license under which this registration is made means that anyone is free to fork meM, extend it, complete the remaining features, or build commercial products on it. The registration documents the work as it stands and makes it available for whatever future development may occur.

**On the position in today's registrations.** Today's session has produced many forward-looking registrations — concepts for RBC, RBI, LFCC, MOTUPER, LMC, and others. meM is the session's first registration of substantial existing work that predates the broader Bible project. The work represents a different era of the registrant's engineering practice — projects developed without the public attribution infrastructure that ideaREG now provides. Bringing meM into the registry connects the registrant's earlier work to the current framework, ensuring that the broader body of engineering contributions has consistent public documentation regardless of when each piece was originally developed.
