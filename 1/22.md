## Idea

### Title

**RBC (RISC-V Basic Compiler)** — a small BASIC-style cross-compiler for RISC-V processors, producing code that fits within 8 KB of combined program and data memory on the target device, with universal resource-movement assignment and embedded assembly support.

### Description

RBC is a proposed cross-compiler for the RISC-V instruction set architecture, designed to extend the registrant's existing AVR Basic Compiler concept to the RISC-V ecosystem. The compiler runs on a development host and produces RISC-V machine code that targets small embedded devices with severe memory constraints.

**Three distinctive design constraints define the compiler:**

**Target memory budget of 8 KB.** The compiler produces RISC-V machine code that fits within 8 KB of combined program memory and data memory on the target device. This is the registration's most consequential technical constraint. The 8 KB budget includes the user's program code, the runtime support code needed to make BASIC features work on the target, and the data the program uses at runtime. Everything must fit within this single budget. The constraint shapes the language design and the code generation throughout — features that would require large runtime libraries, dynamic memory allocation, or substantial bookkeeping cannot be supported because they would consume too much of the 8 KB.

**Universal resource-movement assignment.** The `=` operator must be able to move data between any CPU resource and any other CPU resource. This includes registers, memory locations, stack positions, I/O ports, control and status registers, and any other addressable or accessible resource on the target. The unified syntax for resource movement is a deliberate departure from most high-level languages, which typically distinguish register operations, memory operations, and I/O operations through different language constructs. RBC's approach treats all resource movement as fundamentally the same operation, with the compiler responsible for generating the appropriate instructions for each specific source-destination pair. This gives engineers direct control over resource use without compiler-imposed overhead, which matters when the 8 KB budget requires every byte to be accounted for.

**Embedded assembly support.** The compiler must allow ASM-like optimised code within the BASIC source. This recognises that embedded development on constrained targets often requires hand-tuned instruction sequences for performance-critical sections or for code that needs to be smaller than the compiler's automatic generation produces. RBC programs should be able to drop into assembly when needed without leaving the BASIC source file or requiring separate assembler invocation. For programs running in 8 KB, the ability to hand-optimise specific sections may make the difference between fitting and not fitting.

**Language syntax:**

The syntax should be BASIC/Pascal-like — familiar to engineers who have worked with classical BASIC interpreters or Pascal compilers, accessible to embedded developers who may not have the time to learn complex modern language syntaxes. The BASIC/Pascal lineage is chosen for readability and learnability, not for nostalgia. The languages in this tradition produce code that engineers without recent programming experience can read and modify.

**Predecessor: the AVR Basic Compiler:**

The registrant has previously developed an AVR Basic Compiler — a similar cross-compiler tool targeting Atmel AVR microcontrollers with their similarly constrained memory environments. The AVR Basic Compiler establishes the design pattern: BASIC-style cross-compilation producing tight code for small embedded targets. RBC extends the same pattern to RISC-V, which is increasingly the dominant open-architecture choice for small embedded processors. The relationship between the AVR Basic Compiler and RBC is direct: RBC takes the proven design and applies it to the more contemporary target architecture.

### Why this idea matters

The mainstream embedded development workflow for RISC-V targets typically uses GCC or Clang, with extensive C standard library support, sophisticated optimisation passes, and the assumption that the target has at least tens of kilobytes of memory available for typical programs. This works well for many cases. It does not work well for the smallest RISC-V targets — softcores like SERV that fit in a few hundred LUTs, microcontrollers with very small memories, IoT devices with hard cost constraints, or research platforms where minimal footprint matters.

For these smallest RISC-V targets, the conventional C toolchain produces code that does not fit. The runtime libraries alone often exceed 8 KB. Stripping out unused library functions helps but not enough. Custom minimal libraries can be built but require substantial engineering effort and lose the language's standard features.

RBC addresses this gap. A BASIC-style language with carefully chosen features can produce useful programs in 8 KB. The language design choices — the universal `=` operator, the embedded assembly support, the deliberate absence of features that require large runtime support — are aligned with the constrained target throughout.

Several application domains benefit from this capability:

- **Smallest-class RISC-V softcores** like SERV running on FPGAs with limited block RAM. These targets cannot reasonably run C programs but could run RBC programs.
- **Cost-constrained embedded products** where every byte of memory affects manufacturing cost across volume production.
- **IoT sensor nodes** that must run on minimal hardware to keep power consumption and cost low.
- **Educational embedded computing** where teaching programming on the smallest practical RISC-V target keeps hardware costs low and forces careful programming discipline.
- **Retro-style microcontroller platforms** that intentionally constrain themselves to small memory budgets for the experience of programming under tight constraints.

The combination of the universal resource-movement `=` operator and embedded assembly support addresses the specific needs of bare-metal embedded development on minimal hardware. Engineers can write high-level BASIC code for the bulk of the program and drop into assembly for performance-critical or size-critical sections, all within the same source file and the same compilation step.

### Implementation considerations

A few specific technical observations about how RBC would need to be designed to meet the 8 KB target budget:

**Minimal runtime support.** The compiler must produce code that requires only minimal runtime support on the target. Standard library functions must either not exist (with the language design avoiding the need for them) or be implemented in extremely compact form. Floating-point support, dynamic memory allocation, file I/O, and similar large-runtime features are likely either absent or available only in stripped-down forms.

**Direct code generation.** The compiler should generate compact RISC-V code directly. The universal resource-movement `=` operator gives the compiler enough flexibility that simple code generation can produce tight output. Sophisticated optimisation passes that might produce smaller code in other contexts may not be necessary when the language design already supports compact output.

**Careful instruction selection.** RISC-V's compressed instruction set (the C extension) produces 16-bit instructions for common operations. RBC should preferentially generate compressed instructions where the target supports them, since this can substantially reduce program size.

**The AVR Basic Compiler as the design reference.** The AVR implementation provides most of the design decisions about which features to support and which to omit. Where RISC-V's architecture differs from AVR's, the implementation will need RISC-V-specific choices, but the overall structure of the compiler and the philosophy of language design follow the AVR precedent.

### Domain or field

Embedded systems development, compiler design, RISC-V toolchain, constrained-target programming, BASIC language family, minimal-footprint software design.

### References to related ideas

- **The AVR Basic Compiler** developed previously by the registrant. The direct predecessor that establishes the design pattern for BASIC-style cross-compilation targeting small embedded devices. RBC extends this pattern to RISC-V.
- **The classical BASIC family** of interpreters and compilers — Microsoft BASIC, Commodore BASIC, BBC BASIC, Atari BASIC, GW-BASIC, QuickBASIC. The lineage of BASIC implementations that produced compact code for resource-constrained 8-bit and 16-bit systems.
- **Tiny BASIC** (Dennis Allison, 1975) and similar small BASIC implementations from the early microcomputer era. These demonstrated that useful BASIC compilers and interpreters could produce compact code for very small memory budgets.
- **Forth implementations on RISC-V** and similar minimal-language toolchains for the architecture. RBC complements rather than competes with these, offering BASIC syntax rather than Forth syntax for engineers who prefer the BASIC family.
- **Various contemporary RISC-V softcores** that would be the natural targets for RBC. SERV in particular, with its bit-serial design that minimises FPGA fabric usage, is exactly the kind of target where 8 KB programs make sense and where the standard C toolchain produces output that does not fit. PicoRV32, VexRiscv, NEORV32, Engine-V, and others would also be appropriate targets across various memory budget points.

The specific contribution of RBC is the combination of BASIC/Pascal-like syntax, universal resource-movement assignment, embedded assembly support, and a target memory budget of 8 KB combined program and data, applied to RISC-V as the target architecture.

## Remarks

This registration documents RBC as a concept extending the registrant's existing AVR Basic Compiler. The AVR predecessor provides the proof of concept that BASIC-style compilation can produce tight code for severely constrained embedded targets. RBC applies the same design to RISC-V, which has become the dominant open-architecture choice for small embedded processors in recent years.

**On the 8 KB target budget.** The constraint is deliberately tight. It is set at a point where the conventional C toolchain typically does not produce usable output. The value of RBC is specifically in serving the constrained targets where conventional tools fall short. A 16 KB or 32 KB version would target devices where the conventional toolchain already works adequately, which would defeat the purpose. The 8 KB specification is the distinguishing feature.

**On the language syntax choice.** BASIC/Pascal-style syntax is sometimes seen as outdated in contemporary programming language design. The choice here is deliberate. Engineers in embedded development often have backgrounds that include classical BASIC and Pascal. They can read this syntax without learning a new mental model. For the target use cases — minimal-cost embedded products, smallest RISC-V softcores, educational platforms — accessibility matters more than syntactic sophistication.

**On the universal `=` operator.** The unified syntax for resource movement is the registration's most distinctive language-design choice. This treats RBC as more of a structured assembly than a conventional high-level language in this specific respect. Engineers familiar with assembly programming will recognise that what RBC's `=` operator enables is essentially the unified `mov` instruction concept generalised to all resource pairs. The directness of the operator matches the directness that constrained-target programming requires — no hidden overhead, no abstraction layers that consume bytes the program needs for its own work.

**On the implementation roadmap.** This registration documents the RBC concept. The actual implementation is future work. The AVR Basic Compiler exists; the RBC does not yet. Whether RBC gets implemented by the registrant, by someone else who picks up the idea, or never at all is open. The registration establishes the public record of the concept and makes it available under MIT license for any developer to implement.
