## Idea

### Title

**RBC (RISC-V Basic Compiler)** — a small BASIC-style compiler for RISC-V processors, with universal resource-movement assignment, embedded assembly support, and a total memory footprint of 8 KB or less.

### Description

RBC is a proposed compiler for the RISC-V instruction set architecture, designed to extend the registrant's existing AVR Basic Compiler concept to the RISC-V ecosystem. The compiler targets a specific niche in the embedded development landscape: compilation that can run on the target device itself, with severe memory constraints, while producing optimised code suitable for bare-metal embedded work.

**Three distinctive design constraints define the compiler:**

**Universal resource-movement assignment.** The `=` operator must be able to move data between any CPU resource and any other CPU resource. This includes registers, memory locations, stack positions, I/O ports, control and status registers, and any other addressable or accessible resource on the target. The unified syntax for resource movement is a deliberate departure from most high-level languages, which typically distinguish register operations, memory operations, and I/O operations through different language constructs. RBC's approach treats all resource movement as fundamentally the same operation, with the compiler responsible for generating the appropriate instructions for each specific source-destination pair.

**Embedded assembly support.** The compiler must allow ASM-like optimised code within the BASIC source. This recognises that embedded development on constrained targets often requires hand-tuned instruction sequences for performance-critical sections. RBC programs should be able to drop into assembly when needed without leaving the BASIC source file or requiring separate assembler invocation.

**8 KB total memory footprint.** The entire compiler must be usable with no more than 8 KB of memory total. This constraint is the registration's most consequential technical claim. An 8 KB compiler can run directly on small RISC-V microcontrollers without requiring a separate development host. Programs can be written, compiled, and tested on the target device itself, supporting the kind of interactive embedded development that larger toolchains do not permit.

**Language syntax:**

The syntax should be BASIC/Pascal-like — familiar to engineers who have worked with classical BASIC interpreters or Pascal compilers, accessible to embedded developers who may not have the time to learn complex modern language syntaxes. The BASIC/Pascal lineage is chosen for readability and learnability, not for nostalgia. The languages in this tradition produce code that engineers without recent programming experience can read and modify.

**Predecessor: the AVR Basic Compiler:**

The registrant has previously developed an AVR Basic Compiler — a similar tool targeting Atmel AVR microcontrollers. The AVR Basic Compiler establishes the design pattern and proves the concept on a different small target. RBC extends the same pattern to RISC-V, which is increasingly the dominant open-architecture choice for small embedded processors. The relationship between the AVR Basic Compiler and RBC is direct: RBC takes the proven design and applies it to the more contemporary target.

### Why this idea matters

The mainstream embedded development workflow assumes a powerful host computer doing cross-compilation to a constrained target. This works well for many cases. It does not work well for situations where the host is unavailable, where the target needs to be reprogrammed in the field without specialised equipment, where the development environment must be self-contained on the target, or where engineers want to teach programming on small embedded devices without requiring a separate development computer.

The 8 KB compiler addresses these cases. A compiler that fits in 8 KB can be embedded in the target device's firmware, made accessible through a simple terminal interface, and used to write and modify programs directly on the target. The target becomes both the runtime and the development environment, with no external host required.

Several application domains benefit from this capability:

- **Field-programmable embedded systems** where the target device must be reprogrammed in the field by personnel who do not have access to development hosts.
- **Educational embedded computing** where students learn programming on small devices without needing separate computers.
- **Constrained prototyping** where engineers want to iterate on embedded code without the friction of cross-compilation.
- **Retro-style computing platforms** that emulate the experience of classical home computers where the development environment ran on the same machine as the programs.
- **Industrial controllers** in environments where development hosts cannot be used (clean rooms, hazardous environments, regulated facilities).

The combination of the universal resource-movement `=` operator and embedded assembly support addresses the specific needs of bare-metal embedded development. Engineers can write high-level BASIC code for the bulk of the program and drop into assembly for performance-critical sections or hardware-specific operations, all within the same source file and the same compilation step.

### Implementation considerations

A few specific technical observations about how an 8 KB RISC-V Basic Compiler might be structured:

**Single-pass compilation.** With 8 KB total memory, the compiler cannot afford to build large intermediate representations. Single-pass compilation from source to machine code is likely necessary. This constrains the language design — features that require lookahead or multiple passes (forward references, complex type inference, optimisation across function boundaries) are likely not feasible.

**Symbol table constraints.** The symbol table for variables, labels, and routines must fit within the memory budget alongside the rest of the compiler. This implies relatively short identifier names and limits on the number of distinct symbols per program.

**Direct code generation.** The compiler must generate RISC-V machine code directly without intermediate optimisation passes. The universal resource-movement `=` operator gives the compiler enough flexibility that simple code generation can produce reasonable output without needing sophisticated optimisation.

**The AVR Basic Compiler as the design reference.** The AVR implementation should provide most of the design decisions. Where RISC-V's architecture differs from AVR's, the implementation will need RISC-V-specific choices, but the overall structure of the compiler can follow the AVR precedent.

### Domain or field

Embedded systems development, compiler design, RISC-V toolchain, on-target programming environments, BASIC language family, constrained-memory software design.

### References to related ideas

- **The AVR Basic Compiler** developed previously by the registrant. The direct predecessor that establishes the design pattern. RBC extends this pattern to RISC-V.
- **The classical BASIC family** of interpreters and compilers — Microsoft BASIC, Commodore BASIC, BBC BASIC, Atari BASIC, GW-BASIC, QuickBASIC. The lineage of BASIC implementations that ran on resource-constrained 8-bit and 16-bit systems with development environments that fit on the target machine itself.
- **Tiny BASIC** (Dennis Allison, 1975) and similar small BASIC implementations from the early microcomputer era. These demonstrated that useful BASIC compilers and interpreters could fit in very small memory footprints.
- **Forth implementations on RISC-V** and similar minimal-language toolchains for the architecture. RBC complements rather than competes with these, offering BASIC syntax rather than Forth syntax for engineers who prefer the BASIC family.
- **Various contemporary RISC-V softcores** that would be the natural targets for RBC. SERV, PicoRV32, VexRiscv, NEORV32, Engine-V, and others. RBC would be useful across this ecosystem of small RISC-V implementations.

The specific contribution of RBC is the combination of BASIC/Pascal-like syntax, universal resource-movement assignment, embedded assembly support, and 8 KB total memory footprint, applied to RISC-V as the target architecture.

## Remarks

This registration documents RBC as a concept extending the registrant's existing AVR Basic Compiler. The AVR predecessor provides the proof of concept that an 8 KB Basic compiler is feasible on small embedded targets. RBC applies the same design to RISC-V, which has become the dominant open-architecture choice for small embedded processors in recent years.

**On the 8 KB constraint.** The constraint is deliberately tight. It is not impossible — the AVR Basic Compiler demonstrates that such constraints can be met — but it requires careful design decisions throughout the compiler's implementation. Compilers with looser memory constraints exist; the value of RBC is specifically the discipline that 8 KB imposes. A 16 KB or 32 KB version would be a different tool with different applications. The 8 KB specification is the distinguishing feature.

**On the language syntax choice.** BASIC/Pascal-style syntax is sometimes seen as outdated in contemporary programming language design. The choice here is deliberate. Engineers in embedded development often have backgrounds that include classical BASIC and Pascal. They can read this syntax without learning a new mental model. For the target use cases — field programming, education, constrained prototyping — accessibility matters more than syntactic sophistication.

**On the universal `=` operator.** The unified syntax for resource movement is the registration's most distinctive language-design choice. This treats RBC as more of a structured assembly than a conventional high-level language in this specific respect. Engineers familiar with assembly programming will recognise that what RBC's `=` operator enables is essentially the unified `mov` instruction concept generalised to all resource pairs. Engineers familiar with high-level languages will see this as unusual but consistent — every assignment moves data from somewhere to somewhere, and RBC just makes the model explicit.

**On the implementation roadmap.** This registration documents the RBC concept. The actual implementation is future work. The AVR Basic Compiler exists; the RBC does not yet. Whether RBC gets implemented by the registrant, by someone else who picks up the idea, or never at all is open. The registration establishes the public record of the concept and makes it available under MIT license for any developer to implement.
