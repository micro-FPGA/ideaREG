## Idea

### Title

**PINAPI** — minimal C API for pin-level I/O control, based on opaque pin handles and two-function get/set semantics.

### Description

PINAPI is a small C application programming interface for controlling individual digital I/O pins. The interface consists of two functions and an opaque handle type:

```c
typedef struct pin_descriptor *pin_handle;

void SetPin(pin_handle pin, int value);
int  GetPin(pin_handle pin);
```

**The handle abstraction.** Each pin is represented by an opaque handle. The handle encapsulates the pin's identity, the driver or hardware instance it belongs to, any configuration state, and any other implementation details. Application code holds handles but does not inspect their internals. This lets the implementation evolve without breaking application code, and lets a single application work with pins from many different sources (different chips, different buses, different drivers) through the same uniform interface.

**SetPin semantics.** Calling `SetPin(handle, value)` configures the pin as an output (if it was not already) and drives the specified value. The value is logically boolean — zero or non-zero — though the parameter type is `int` to fit C conventions.

**GetPin semantics.** Calling `GetPin(handle)` configures the pin as an input (if it was not already) and returns the current value at the pin. The return value is logically boolean, returned as `int`.

The interface is minimal by design. There is no separate direction control function, no configuration function, no initialisation function visible to the application. Pin handles are obtained from whatever driver or system layer the application is using, then passed to SetPin and GetPin as needed. The application's experience of pin control is reduced to these two operations.

### Why this interface

The PINAPI design solves a specific problem cleanly. Pin control across diverse hardware is one of the most common operations in embedded software, and the interfaces available historically have ranged from awkward to incompatible. Hardware-specific GPIO APIs vary between chip families, between vendor toolchains, between operating systems. An application that needs to work across multiple platforms ends up with conditional compilation, abstraction layers, or both.

PINAPI provides a uniform interface that any platform can implement. The two-function structure is small enough to be implemented as a thin wrapper around any underlying GPIO mechanism — direct register access, OS-provided GPIO drivers, memory-mapped peripherals, AXI-Lite bus transactions, USB-to-GPIO bridges, network-attached GPIO, or anything else. The opaque handle lets implementations vary widely in what they do internally while presenting the same application-visible interface.

The benefits in practice:

- **Portability.** Application code that uses PINAPI works against any implementation. Changing the underlying hardware requires changing only the handle source, not the application logic.
- **Simplicity.** Two functions. Easy to teach, easy to remember, easy to use correctly.
- **Composability.** An application can mix pins from different sources (some pins from the local FPGA, some from a remote I2C expander, some from a virtual pin in software) by using handles obtained from different driver layers, all through the same SetPin/GetPin interface.
- **Abstraction strength.** The implementation can change the underlying mechanism (different bus protocol, different addressing scheme, different hardware) without any application change.

### Historical context

PINAPI has been used in the registrant's private engineering practice since 1990. It has been applied across many projects, on many hardware platforms, in many products. The interface has remained stable across the full period — the same two functions, the same handle semantics, the same minimal design.

The interface emerged from the practical need to control pins on diverse hardware in a way that produced portable, maintainable application code. The thirty-five years of use without significant revision is itself evidence of the interface's correctness — engineering interfaces that need frequent change are usually addressing the wrong abstraction.

### A note on convergent design

On 2026-05-08, the day this registration is being made, Identor #9 (Claude, Anthropic's AI assistant) independently drafted a C library specification for the MicroFPGA concept (also registered in this repository on the same day). The drafted specification arrived at functionally equivalent two-function get/set semantics, with the function names being `asio_write(pin, value)` and `asio_read(pin)` rather than PINAPI's `SetPin(handle, value)` and `GetPin(handle)`.

The convergence is meaningful. Engineering interfaces that get reinvented by independent thinkers are interfaces that match the structure of the problem. PINAPI's design is not idiosyncratic preference; it is the natural shape of the pin-control abstraction. Other engineers working on the same problem will continue to arrive at the same answer.

This registration captures PINAPI as the established prior art for this interface pattern. Future engineers who arrive at similar designs can identify the convergence and reference PINAPI as the first articulation.

### Domain or field

Embedded systems software, hardware abstraction layers, GPIO control, driver APIs, portable software interfaces, FPGA development tooling.

### References to related ideas

- **Various platform-specific GPIO APIs.** Linux GPIO sysfs interface, FreeRTOS GPIO drivers, vendor-specific HAL libraries (CMSIS, ESP-IDF, MicroPython's machine.Pin, Arduino's digitalWrite/digitalRead, and many others). Each provides similar functionality but with different interfaces. PINAPI's contribution is the minimal uniform interface that abstracts over all of these.
- **POSIX file I/O.** The same abstraction pattern — opaque handle, minimal operation set, uniform interface across many backing implementations. PINAPI is the GPIO analogue of file descriptors.
- **The Arduino digitalWrite/digitalRead interface.** Closest analogue in widespread modern use. Arduino uses pin numbers as integers rather than opaque handles. PINAPI's handle abstraction is the more capable design, though Arduino's integer pin numbers are simpler for the Arduino target audience.
- **The ASIO IP core** (also registered in this repository on 2026-05-08). ASIO's memory-mapped per-pin access is one of the natural backing implementations for PINAPI — each pin's address corresponds to one pin handle, and SetPin/GetPin become single AXI-Lite transactions.

The specific contribution of PINAPI is the minimal opaque-handle two-function interface, established in 1990 and maintained in continuous use since then.

## Remarks

PINAPI is unusual in this registry because it is not a new idea. It is an engineering interface that has been in private practical use for thirty-five years. The registration documents what already exists rather than introducing what is new.

The decision to register PINAPI now is partly retrospective and partly forward-looking. Retrospectively, it captures the public record of when the interface was first designed and by whom, after thirty-five years in which the interface had no public registration. Forward-looking, it establishes prior art that future engineers can reference when they arrive at similar designs independently, as Identor #9 did earlier today during the MicroFPGA drafting.

The registration is made under MIT License, releasing the interface for general use. PINAPI implementations may be created freely by any party. The interface itself is in the public commons by virtue of this registration; the design has never been commercially restricted by the registrant.

If PINAPI is adopted as the C interface for MicroFPGA (which would be the natural and appropriate choice), the lineage will be visible — PINAPI was the prior interface design from 1990, ASIO is the IP core from 2026 that makes a natural backing implementation, and MicroFPGA is the product concept that combines them with pre-built bitstreams and a simplified toolchain.

The interface's longevity is itself a small piece of evidence about how engineering work persists. Designs that solve real problems cleanly tend to be used long after they are first articulated, sometimes by their original designers across decades of practice, sometimes by independent reinventors who arrive at the same answer through their own thinking. PINAPI has been used by its original designer for thirty-five years. Whether others have independently designed similar interfaces in private practice is unknown; the registration makes the design public so the question becomes answerable going forward.
