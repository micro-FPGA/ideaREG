## Idea

### Title

**RBI (RISC-V Basic Interpreter)** — a Basic-Stamp-style BASIC interpreter for RISC-V processors, with the interpreter fitting in 8 KB of code memory, a minimalistic UART-based editor, program tokens stored in Lattice UFM or external I2C EEPROM, and support for calling assembly routines from BASIC code.

### Description

RBI is a proposed BASIC interpreter for the RISC-V instruction set architecture, designed to bring the Basic Stamp development model to RISC-V softcores and microcontrollers. The interpreter runs on the target device itself, executing tokenised BASIC programs stored in non-volatile memory. The user develops programs interactively through a UART terminal connection, with no external compilation step required.

**The Basic Stamp model:**

The Basic Stamp from Parallax established the development model that RBI extends to RISC-V. A small embedded board runs a BASIC interpreter as fixed firmware. The user's BASIC program is stored separately in EEPROM. The user connects a terminal program to the board's serial interface, edits the program line by line, saves changes to EEPROM, and runs the program. The development cycle is edit-save-run, all on the target hardware, with no host-side toolchain involvement after the initial interpreter firmware is loaded.

This model was widely successful in education, hobby electronics, and rapid prototyping for two reasons. First, it eliminated the friction of cross-compilation. Engineers could iterate on embedded code as quickly as they could iterate on home computer BASIC programs in the 1980s. Second, it provided a complete self-contained development environment on the target — useful for teaching, field programming, and any situation where bringing a separate development computer is inconvenient or impossible.

RBI proposes this same model for RISC-V, taking advantage of the rich ecosystem of small RISC-V softcores and microcontrollers that has developed in recent years.

**Four distinctive components define RBI:**

**Interpreter footprint of 8 KB.** The interpreter itself must fit in 8 KB of code memory on the target device. This is the firmware that the user loads once and that remains in place across all subsequent program development. The 8 KB budget includes the BASIC tokeniser, the parser, the execution engine, the runtime library, the editor, and the non-volatile memory access routines. Everything that makes RBI work as a development environment must fit in this 8 KB.

**Minimalistic UART-based editor.** The editor provides the user interface through a serial terminal connection. The editor supports the standard BASIC interactive workflow: list the program, add or modify lines by typing line numbers followed by code, delete lines, save the program to non-volatile memory, and run the program. The editor is intentionally minimal — no syntax highlighting, no multi-line editing, no full-screen interface. The goal is the basic edit-save-run cycle that makes the development model usable, not sophisticated editing features.

**Token storage in UFM or external I2C EEPROM.** The user's BASIC program is stored as tokens (compact binary representations of the BASIC source) in non-volatile memory separate from the interpreter's code memory. Two storage options are supported. The first is UFM (User Flash Memory), the on-chip non-volatile memory block available in many Lattice FPGAs (MachXO2, MachXO3, MachXO5, and similar parts). UFM is convenient because it is internal to the FPGA and requires no external components. The second is external I2C EEPROM, which extends RBI to targets without UFM or with larger storage requirements than UFM provides. The I2C interface is simple enough to implement in the small budget the interpreter has available.

**Assembly routine calls.** The interpreter must support calling assembly routines from BASIC code. The user writes performance-critical or hardware-specific sections in RISC-V assembly, places them in a known location, and invokes them from BASIC. The assembly routines run at full processor speed without interpreter overhead, allowing the program to combine high-level BASIC logic with bare-metal assembly performance where needed.

### Language characteristics

The BASIC dialect used by RBI should follow the classical BASIC family — Microsoft BASIC, PBASIC, or similar — with the specific syntactic choices made to fit the constraints of the 8 KB interpreter footprint.

Features that are likely supported:

- Variables with integer and string types
- Basic arithmetic and logical operators
- Line-numbered program structure
- GOTO and GOSUB control flow
- IF/THEN conditionals
- FOR/NEXT loops
- PRINT for serial output
- INPUT for serial input
- I/O operations for accessing the target hardware
- Token-based program storage for compact representation

Features that are likely not supported in the 8 KB interpreter:

- Floating-point arithmetic (unless RISC-V hardware floating-point is available and trivially accessible)
- Dynamic memory allocation
- File I/O beyond the non-volatile program storage
- Sophisticated string manipulation
- User-defined functions (subroutines via GOSUB instead)
- Multitasking or interrupt handling from BASIC

### Why this idea matters

The conventional RISC-V embedded development workflow assumes a development host running GCC or Clang, with the user writing C code, cross-compiling to RISC-V machine code, and flashing the result to the target. This works well for most cases. It does not provide the interactive development experience that the Basic Stamp model offers.

For specific use cases, the interactive on-target development model has substantial value:

- **Educational embedded computing.** Students learning programming benefit from the immediate feedback loop of edit-save-run on the target itself. The Basic Stamp's success in education is the existing evidence.
- **Rapid prototyping.** Engineers iterating on a concept can develop and test directly on the target without the friction of repeated cross-compilation cycles.
- **Field programming.** Personnel maintaining deployed embedded systems can modify programs in the field without bringing development hosts to the deployment site.
- **Hobbyist electronics.** Makers and hobbyists who want to use RISC-V hardware benefit from the same accessible programming model that the Basic Stamp provided for PIC.
- **Lattice FPGA platforms specifically.** Lattice's UFM-equipped parts and the various small RISC-V softcores that target Lattice FPGAs (SERV, PicoRV32, NEORV32, and others) form a natural ecosystem where RBI would be useful. The interpreter could be deployed as a standard component of small RISC-V FPGA designs, giving these designs the Basic-Stamp-style development experience.

The assembly routine calling capability bridges the use case. Engineers who need performance can write the performance-critical sections in assembly while keeping the bulk of the program in interactive BASIC. This combination serves both the educational and the practical applications.

### The relationship to RBC (RISC-V Basic Compiler)

RBI and RBC are complementary tools registered separately in this registry on the same date.

**RBC** is a cross-compiler. It runs on a development host and produces RISC-V machine code that fits in 8 KB on the target. Programs compiled with RBC run at full processor speed with no interpreter overhead. The development workflow is conventional: write source on the host, compile, flash to target, run.

**RBI** is an interpreter. It runs on the target itself, executing tokenised BASIC programs from non-volatile memory. Programs interpreted by RBI run more slowly than equivalent compiled code, but the development workflow is interactive: edit, save, and run all on the target with no host-side step.

Engineers choose between RBC and RBI based on which trade-off serves their use case better. For maximum performance and minimum program memory footprint, RBC is appropriate. For interactive on-target development and the educational use cases that benefit from the Basic Stamp model, RBI is appropriate. The two tools cover the BASIC programming model on RISC-V across both ends of the host-versus-target development spectrum.

### References to related ideas

- **The Basic Stamp from Parallax.** The direct conceptual ancestor of RBI. Parallax's BASIC interpreter for PIC microcontrollers established the development model that RBI extends to RISC-V.
- **PBASIC** — the BASIC dialect used by the Basic Stamp. RBI's language design draws on PBASIC's example of a BASIC dialect adapted for embedded constraints.
- **The classical BASIC family** of home computer interpreters from the 1980s. Microsoft BASIC, BBC BASIC, Commodore BASIC, Atari BASIC, and others. The interactive edit-save-run development model that RBI uses on the target was the standard development model for these home computers.
- **MicroPython, CircuitPython.** Modern interactive on-target programming environments using Python instead of BASIC. These demonstrate that the on-target development model continues to have value in contemporary embedded computing. RBI offers the same model for engineers and educators who prefer BASIC's syntactic simplicity.
- **RBC (RISC-V Basic Compiler)** registered separately in this registry on 2026-05-15. The compiled-output complement to RBI's interpreted-on-target model.
- **Lattice UFM (User Flash Memory).** The on-chip non-volatile memory in Lattice MachXO2, MachXO3, MachXO5, and similar parts. RBI's primary token storage mechanism on Lattice FPGA platforms.
- **Various contemporary RISC-V softcores** that would be the natural targets for RBI. SERV, PicoRV32, NEORV32, VexRiscv, Engine-V, and others. RBI would be useful across this ecosystem of small RISC-V implementations, particularly when paired with Lattice FPGAs that provide UFM for token storage.

The specific contribution of RBI is the combination of an 8 KB interpreter footprint, the Basic-Stamp-style on-target development model, Lattice UFM and I2C EEPROM token storage options, and assembly routine calling support, applied to RISC-V as the target architecture.

## Remarks

This registration documents RBI as a concept that extends the proven Basic Stamp development model to RISC-V. The Basic Stamp's success across decades of embedded development demonstrates that the interactive on-target BASIC model has real value. RBI applies the same model to the contemporary RISC-V ecosystem.

**On the interpreter footprint.** The 8 KB constraint for the interpreter itself is the registration's most consequential technical claim. This is not the user's program memory budget; it is the interpreter firmware budget. The user's BASIC program is stored separately in UFM or external EEPROM and can be substantially larger than the interpreter itself. The 8 KB applies specifically to the fixed firmware that makes RBI work as a development environment.

**On the assembly routine calling support.** This feature is what distinguishes RBI from a pure interpreter and what makes it practically useful for embedded applications that need performance somewhere in the program. Engineers can write the bulk of the application logic in interpreted BASIC for development simplicity, then write the performance-critical or hardware-specific sections in assembly for maximum speed. The combination serves applications that pure BASIC could not handle and that pure assembly would be too tedious to develop in.

**On the Lattice FPGA target.** RBI is specifically designed with Lattice's UFM-equipped FPGAs in mind. The UFM block provides convenient on-chip non-volatile storage for the user's BASIC program tokens, allowing RBI deployments on Lattice parts to be self-contained without external memory components. This makes Lattice FPGAs a particularly clean target for RBI. Other FPGA vendors with similar on-chip non-volatile memory could also be targeted, and the external I2C EEPROM option extends RBI to FPGAs without on-chip non-volatile memory.

**On the implementation roadmap.** This registration documents the RBI concept. The actual implementation is future work. Whether RBI gets implemented by the registrant, by someone else who picks up the idea, or never at all is open. The registration establishes the public record of the concept and makes it available under MIT license for any developer to implement.

The registration is connected to the RBC (RISC-V Basic Compiler) registration also made on 2026-05-15. Together, RBC and RBI cover the BASIC programming model on RISC-V across both the compiled and interpreted development paradigms. Engineers choosing between the two tools select based on which trade-off — compilation overhead versus interpretation overhead, host development versus on-target development — better fits their specific use case.
